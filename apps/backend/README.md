# apps/backend

The PulseNote backend: a **FastAPI** app in **Docker** that stores cases as FHIR R4 `QuestionnaireResponse`s, one JSON file per case.

It also serves the web app ([`apps/web`](../web)) at `/`, and the form preview from [`packages/form-definitions/preview.html`](../../packages/form-definitions/preview.html) at `/preview`.

**Owner:** Area 2 (Backend & FHIR / IPS modelling)

## Run

With Docker (from this folder):

```bash
cp .env.example .env              # optional: change APP_PORT (default 8014)
docker compose up -d --build
```

- Web app: <http://localhost:8014/>
- Form preview: <http://localhost:8014/preview>
- API docs (OpenAPI, generated by FastAPI): <http://localhost:8014/api/docs>

For live editing, add the dev override. It mounts `app/`, `apps/web` and `packages/form-definitions` and reloads on code changes:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

Without Docker, with [uv](https://docs.astral.sh/uv/):

```bash
uv run uvicorn app.main:app --reload --port 8014
uv run pytest
```

Questionnaires are loaded at startup, so restart after changing a form. The web app and the preview page are read from disk on every request, so edits to them need no restart.

## API

All routes are under `/api`. The interactive OpenAPI docs are at `/api/docs`, the spec at `/api/openapi.json`.

**Conventions**

- **Format:** requests and responses are FHIR R4 JSON. Responses use `Content-Type: application/fhir+json`; requests may send `application/fhir+json` or `application/json`.
- **Errors:** every error is a FHIR `OperationOutcome` with one `issue` per problem:

  ```json
  {
    "resourceType": "OperationOutcome",
    "issue": [
      {
        "severity": "error",
        "code": "not-found",
        "diagnostics": "Case 'abc-1' not found"
      }
    ]
  }
  ```

- **Lists:** returned as a FHIR `Bundle` of type `searchset`. Each `entry` holds the full resource, plus its URL in `fullUrl`.
- **Auth:** none yet. Every client sees and may change every case.

| Endpoint                                 | Purpose                                                    |
| ---------------------------------------- | ---------------------------------------------------------- |
| [`GET /api/cases`](#get-apicases)                         | List cases                                |
| [`GET /api/cases/{id}`](#get-apicasesid)                  | Load a case                               |
| [`PUT /api/cases/{id}`](#put-apicasesid)                  | Create or update a case                   |
| [`DELETE /api/cases/{id}`](#delete-apicasesid)            | Delete a case                             |
| [`GET /api/cases/{id}/text`](#get-apicasesidtext)         | Free-text report (**not implemented yet**) |
| [`GET /api/cases/{id}/export`](#get-apicasesidexport)         | Patient FHIR document / IPS (**not implemented yet**) |
| [`GET /api/questionnaires`](#get-apiquestionnaires)       | List form definitions                     |
| [`GET /api/questionnaires/{id}`](#get-apiquestionnairesid) | Load a form definition                   |

### Cases

A case **is** a FHIR `QuestionnaireResponse`: the answers of one patient to one form. There is no separate case format.

**Case id:** created on the phone, not by the server, so sending the same case again after a dropped connection updates it instead of creating a duplicate. It must be a valid FHIR `id`: letters, digits, `-` and `.`, up to 64 characters. A UUID works. An invalid id in the URL is rejected with `422`.

**Server-managed fields:** the server sets `id` (from the URL), `meta.versionId` (`"1"`, `"2"`, … per save) and `meta.lastUpdated` (UTC timestamp). Other `meta` content sent by the client (e.g. `profile`, `tag`) is kept.

A stored case looks like this:

```json
{
  "resourceType": "QuestionnaireResponse",
  "id": "3f2a9c1e-0b7d-4e1a-9a52-6c1d2e8f4b10",
  "meta": { "versionId": "2", "lastUpdated": "2026-11-23T14:35:12.408Z" },
  "questionnaire": "https://pulsenote.example/Questionnaire/ed-surgery|0.1",
  "status": "in-progress",
  "authored": "2026-11-23T14:30:00Z",
  "item": [
    {
      "linkId": "patient",
      "item": [
        { "linkId": "patient-family-name", "answer": [{ "valueString": "Muster" }] },
        { "linkId": "patient-birth-date", "answer": [{ "valueDate": "1950-04-01" }] }
      ]
    }
  ]
}
```

#### `GET /api/cases`

Lists the stored cases, newest (`meta.lastUpdated`) first. Each entry contains the **complete** case. There is no paging yet.

| Query parameter | Example | Effect |
| --- | --- | --- |
| `questionnaire` | `https://pulsenote.example/Questionnaire/ed-surgery` | Cases of this form, all versions |
|                 | `https://pulsenote.example/Questionnaire/ed-surgery\|0.1` | Cases of exactly this form version |
| `status`        | `in-progress`, `completed` | Cases with this `QuestionnaireResponse.status` |

```
GET /api/cases?status=completed

200 OK
{
  "resourceType": "Bundle",
  "type": "searchset",
  "timestamp": "2026-11-23T15:00:00.000Z",
  "total": 1,
  "entry": [
    {
      "fullUrl": "http://localhost:8014/api/cases/3f2a9c1e-…",
      "resource": { "resourceType": "QuestionnaireResponse", "id": "3f2a9c1e-…", … },
      "search": { "mode": "match" }
    }
  ]
}
```

No matches is not an error: `200` with `"total": 0` and an empty `entry` list.

#### `GET /api/cases/{id}`

Returns one case as stored, with headers `ETag: W/"<versionId>"` and `Last-Modified: <lastUpdated>`.

| Status | When |
| --- | --- |
| `200` | Found |
| `404` | No case with this id |
| `422` | The id is not a valid FHIR id |

#### `PUT /api/cases/{id}`

Creates the case if the id is new, otherwise **replaces** it completely. There is no partial update: always send the whole `QuestionnaireResponse`.

Requirements for the body:

- `resourceType` is `QuestionnaireResponse`.
- `id` may be left out. If it is given, it must equal the id in the URL.
- `questionnaire` names the exact form version as `<url>|<version>`, e.g. `https://pulsenote.example/Questionnaire/ed-surgery|0.1`. That version must be loaded by the server (see [Form versions](#form-versions)).
- `status` is one of `in-progress`, `completed`, `amended`, `entered-in-error`, `stopped`.
- The answers pass the [validation](#validation).

The response body is the stored case, including `id` and `meta`.

| Status | When | Headers |
| --- | --- | --- |
| `201` | Created | `Location` (URL of the case), `ETag`, `Last-Modified` |
| `200` | Updated (`meta.versionId` + 1) | `ETag`, `Last-Modified` |
| `400` | `id` in the body differs from the URL | |
| `422` | Invalid case: the `OperationOutcome` lists **all** problems, or the URL id is not a valid FHIR id | |

Example error, with one `expression` per problem pointing at the item:

```json
{
  "resourceType": "OperationOutcome",
  "issue": [
    {
      "severity": "error",
      "code": "value",
      "diagnostics": "Value of 'body-height' is greater than the maximum 250",
      "expression": ["QuestionnaireResponse.item[0].item[4].item[0].answer[0]"]
    },
    {
      "severity": "error",
      "code": "business-rule",
      "diagnostics": "Item 'pain-nrs' is answered but disabled by enableWhen",
      "expression": ["QuestionnaireResponse.item[1].item[0].item[1]"]
    }
  ]
}
```

The last save wins: if the phone and the desktop edit the same case, the later `PUT` overwrites the earlier one. There is no `If-Match` check yet.

#### Validation

Two stages, run on every `PUT`:

1. **FHIR R4B structure**, using [fhir.resources](https://github.com/nazrulworld/fhir.resources):
   - known elements only, datatype formats (dates, decimals, …) and required elements
   - exactly one `value[x]` per answer and a valid `status`
   - R4B's `QuestionnaireResponse` is the same as R4's.
   - This checks the base specification only: no profiles, invariants or terminology.
2. **Against the referenced `Questionnaire`:**
   - each `linkId` exists at that position, items keep the form's order, and only repeating groups appear more than once
   - the answer type matches the item type: `boolean` → `valueBoolean`, `decimal` → `valueDecimal`, `integer` → `valueInteger`, `date` → `valueDate`, `string`/`text` → `valueString`, `quantity` → `valueQuantity`, …
   - `choice` answers are one of the `answerOption`s (or of a contained `answerValueSet`). `open-choice` also allows a free-text `valueString`.
   - an option marked exclusive (e.g. "normal", "unknown") is the only answer
   - `repeats`, `minValue`/`maxValue`, `maxLength`/`minLength` and quantity units are respected
   - group and display items have no answers; child items of a question are nested under its `answer`
   - items disabled by `enableWhen` have no answers. This uses the same logic as the preview: `!=` with no answer counts as true.
   - every enabled `required` item is answered, **whatever the `status`**. Inside a group this applies only if the group is present.

Answers bound to an external ValueSet (not contained in the `Questionnaire`) cannot be checked yet, because there is no terminology server.

#### `DELETE /api/cases/{id}`

Deletes the case file permanently. There is no history and no undo.

| Status | When |
| --- | --- |
| `204` | Deleted (no body) |
| `404` | No case with this id |

The retention period after transfer to the HIS is not decided yet. Until then, cases are only deleted through this endpoint.

#### `GET /api/cases/{id}/text`

**Not implemented yet.** It will return the free-text report of a case, to copy into the HIS. Its structure and wording are owned by area 1.

| Status | When |
| --- | --- |
| `501` | Case exists (`OperationOutcome` with code `not-supported`) |
| `404` | No case with this id |

#### `GET /api/cases/{id}/export`

**Not implemented yet.** It will turn the case's answers into standard FHIR resources and return them as an IPS document. The steps are:

1. **Extraction:** answers become resources, following the [mapping table](../../docs/mapping/ed-surgery.csv):
   - `Patient` from the patient fields
   - one `Observation` per vital sign (LOINC + UCUM)
   - `AllergyIntolerance`, `MedicationStatement`, `Condition` and `Procedure` from the history
   - an `Encounter` (class `EMER`) for the ED visit
2. **Packaging:** a `Bundle` of type `document`. Its first entry is a `Composition` (LOINC `60591-5`) whose sections (Problems, Allergies, Medication, Vital signs, …) reference those resources. The form's "No" answers fill the required IPS sections with "none known" codes.

The physical exam and ED details (room, GP, …) are not part of the IPS. If they are needed as FHIR later, a `collection` Bundle of the full case would be returned instead. Conformance to the IPS profiles is checked with the HL7 FHIR Validator, not at runtime.

| Status | When |
| --- | --- |
| `501` | Case exists (`OperationOutcome` with code `not-supported`) |
| `404` | No case with this id |

### Questionnaires

Read-only access to the form definitions the server loaded at startup from `packages/form-definitions/questionnaires/`. These are exactly the versions `PUT /api/cases/{id}` validates against. The web app can therefore load its templates from here instead of keeping its own copies.

#### `GET /api/questionnaires`

Lists every loaded `Questionnaire`, **every version**, sorted by `url`, then version. Each entry contains the complete form definition.

| Query parameter | Example | Effect |
| --- | --- | --- |
| `url`     | `https://pulsenote.example/Questionnaire/ed-surgery` | Only this form |
| `version` | `0.1` | Only this version |

```
GET /api/questionnaires?url=https://pulsenote.example/Questionnaire/ed-surgery

200 OK
{
  "resourceType": "Bundle",
  "type": "searchset",
  "total": 1,
  "entry": [
    {
      "fullUrl": "http://localhost:8014/api/questionnaires/ed-surgery?version=0.1",
      "resource": { "resourceType": "Questionnaire", "id": "ed-surgery", "version": "0.1", … },
      "search": { "mode": "match" }
    }
  ]
}
```

#### `GET /api/questionnaires/{id}`

Returns one form by its `Questionnaire.id` (e.g. `ed-surgery`): the **newest** version, or the one given with `?version=`.

| Status | When |
| --- | --- |
| `200` | Found |
| `404` | Unknown id, or that version does not exist |

## Form versions

Every `*.json` `Questionnaire` below `packages/form-definitions/questionnaires/`, in any subfolder, is loaded and indexed by `url|version`. The backend accepts cases built with older form versions (from phones running an older app version) as long as that version's file is kept. For example, move the old file to `questionnaires/archive/` before raising `version`.

## Storage

One JSON file per case in `DATA_DIR/cases/<id>.json`: `apps/backend/data/` (ignored by git), both when run locally and in Docker, where that folder is bind-mounted at `/data`. Writes are atomic (temp file + rename). The server runs a **single worker**, because writes are serialized with an in-process lock.

**Data protection:** synthetic patients only. The backend is a temporary case store, not the patient record. See "Data protection & security" in the root README.
